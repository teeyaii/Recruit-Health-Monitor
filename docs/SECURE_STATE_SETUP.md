# STEVE 1.0 — secure persistence and private recruit health notes

**Status:** Implementation is optional until owner configures a verified private database and new secrets. Do not enter real health/diagnosis data into existing Render Free RAM mode. This is a prototype, not approved medical record storage or continuous safety monitoring.

## Provision the remote encrypted snapshot store

1. Create a **private Supabase project** under an account authorized to hold the data. Confirm data processing, retention, personnel permissions, Thailand legal/policy requirements, and residency with the responsible authority **before** processing any real recruit medical information.
2. In the project's SQL editor, create the minimal ciphertext-only table (no recruit names or clear health data):

```sql
create table if not exists public.steve_secure_state (
 id text primary key,
 envelope text not null,
 updated_at timestamptz not null default now()
);
alter table public.steve_secure_state enable row level security;
revoke all on table public.steve_secure_state from anon, authenticated;
grant select, insert, update on table public.steve_secure_state to service_role;
```

There are **no anon/authenticated SELECT policies**. The private service-role key is confined to the backend. It bypasses RLS, so possession of that key is highly sensitive. Protect the Supabase project, backups, database logs and service-role key.

3. In the existing **Render service → Environment**, configure all three independently and privately:
   - `STEVE_SUPABASE_URL` — project URL (`https://<project>.supabase.co`)
   - `STEVE_SUPABASE_SERVICE_ROLE_KEY` — **preferred: modern `sb_secret_...` key** from Supabase Settings → API Keys → Secret keys; legacy service-role JWT is supported for compatibility (backend only, >=32 chars). Never use the public `sb_publishable_...` or legacy `anon` key.
   - `STEVE_DATA_ENCRYPTION_KEY` — **independent cryptographically random 32-byte AES key encoded as standard Base64**, generated by a secure random generator. Do not use a memorable password, 4-digit code or a Gateway token. Keep a securely managed backup: losing the key makes stored ciphertext unreadable.

Don't put these in GitHub, screenshots, a URL, Bluefy, localStorage or a frontend. Don't copy or reveal key values in a support conversation.

## Persistence behavior

When all keys are set, the server **loads and authenticates** the encrypted snapshot before listening for requests. If remote storage is unavailable, invalid or the encryption key is wrong, startup intentionally refuses to claim durable operation. Partial configuration is rejected. Without all keys the existing live Dashboard/2-band demonstration remains in RAM-only mode, and **private health entry is disabled (503)**.

An authenticated service writes the roster, group phase/audit, optional personal profiles, weather context and bounded rolling pulse-history to the single encrypted snapshot. Important roster/phase/profile edits await confirmation. Accepted BPM history is checkpointed at 30-second intervals; an unexpected crash may lose up to a checkpoint interval of recent samples. Data are encrypted in the Node.js server with AES-256-GCM before HTTPS upload to Supabase, compressed before encryption. Supabase stores only one ciphertext envelope. RAM-only data are NOT automatically migrated from an earlier Render deployment. A database only protects server-stored history against restarts; it cannot capture BPM while Bluefy stops sending, and doesn't make Render Free always-on.

**Operational limitations:** This is a single-writer prototype. Do not scale Render replicas or add independent writing processes against the same row without server-side distributed revisions/locking. Secure retention, formal incident response, authorized medical access policy, consent/legal basis, backup recovery, rotation/revocation, audit and resilience requirements must be reviewed before operational deployment.

## Private personnel form

Authenticated **trainer and medical roles only** see the collapsed “ข้อมูลส่วนตัว” section inside the registration controls. The original legacy Viewer role and Gateway sessions cannot read/write these fields. Encrypted fields: **weight kg**, **height cm**, **condition/precaution notes** (up to 300 characters). BMI is **derived** from kg/(m)^2 to one decimal when both values exist, not used as a safety or return-to-training determination. The form is never shown on the public commander Dashboard/cards, SSE, Gateway, or audit and does not appear in the chart API. Changing wearer code clears old wearer's notes and history.

For existing users logging in only with the shared Viewer token, configure **unique** `STEVE_TRAINER_TOKEN` and `STEVE_MEDIC_TOKEN` (32+ characters each) before authorized use, while retaining the distinct 32+ character Viewer and Gateway secrets.

## Gateway sessions

Browser Gateway G01, G02, G03 now have 10-hour **absolute** authenticated cookies (36,000 seconds) with revocation on logout; G04/G05 stay at 2 hours (7,200 seconds). Cookie remains HttpOnly, Secure in production, SameSite Strict. **Session continuity does not keep BLE running in the iPhone background, prevent Render Free sleeping, or maintain uploads after network loss.** Expired sessions need re-authentication; no secrets are saved in localStorage.
